1两个问题，一个根因

#1470 与输出上限

问题原因
DeepSeek 等模型在 OpenAI 形状的 client 上选不到 max档位要与一条按 client_type 写的规则取交集，openai-completions / openai-responses 上去掉 max，发请求时再改写成 xhigh
输出上限用户无法设置请求侧只用 generation_limits.go 的常量（预留 8192，思考时 32000）；回复被截断时按正常完成处理

改之前：档位被线格式筛

  • openai-completions 上档位去掉 max
  • 发请求时 max → xhigh 改写
  • DeepSeek / OpenRouter 上的 Claude 因此选不到 max
  • 已存的 max 在回退中落到 low，并被写回设置

改之后：只认模型声明

  • 档位只来自模型声明的列表
  • 思考机制（adaptive / budget / toggle / always）只来自声明
  • 同一种请求体上，上限为 xhigh 与为 max 的模型都能选到各自的最高档
档位不能用来推断思考机制：Opus 4.5 有 effort 档位，却只接受 budget_tokens；Opus 4.6 有 max 没有 xhigh，却是 adaptive。因此机制只读模型声明，未声明的 Claude 模型仍按 Anthropic 文档的代际规则判定。

4为什么不能从档位反推机制

档位列表与「哪条线路承载思考控制」是两个独立事实。同一个列表可以对应不同的线路，同一代际的模型也可以有不同的档位。

模型声明的档位实际线路
claude-opus-4-5[low, medium, high]budget_tokens（不接受 effort 字段）
claude-opus-4-6[low, medium, high, max]adaptive + effort
gemini-2.5-pro[low, medium, high]thinkingBudget（token 数）
gemini-3.1-pro[low, medium, high]thinkingLevel（具名档位）
Gemini 2.5 与 3.1 的档位列表相同，线路互斥（同时发两个字段是 400）。因此机制只读模型显式声明，未声明的 Claude 模型仍按 Anthropic 文档的代际规则判定。

5迁移 0166 归一化旧拼写

旧数据里存在两种已废弃的档位拼写，本迁移把它们归一：none → disable；adaptive 在「无法关闭」的模型上 → disable，其余 → medium。

迁移连接不设 memoh.team_id，而 bots、bot_sessions、schedule、models 都在 FORCE RLS 下；不抬起策略就报错中止。四张表都要抬起并在末尾按相反顺序复位。

编号 0166 而非 0165：另有两个未合并的 PR（#1564、#1550）已占用 0165。空档是允许的（main 自身在 101 处就有空档），已在本机实测迁移可从 164 直接应用 0166。
